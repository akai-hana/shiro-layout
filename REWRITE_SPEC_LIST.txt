ANALYZER ARCHITECTURE:
(these are bigger, structural/architectural tasks. sub-divide into smaller tasks if needed)

- analyzer divided into three big directories: `core/`, `utils/`, `config/`

  - `core/` contains core analyzer and refiner (annealer)
    - analyzer, annealer (now renamed to analyze.py/compute.py), and audit_shai.py should be corpus-independent, where you should be able to pass it any given corpus through command runtime flags instead. (audit_shai.py should also be renamed to audit.py)
    - annealer (compute) should only consider primary-corpus sacrifice over secondary-corpus improvement right at the end of the primary optimization (when it is determined that the computed layout can no longer be realistically improved). this way, only one corpus pass and score is done and considered per iteration (the primary), while the secondary corpus is a thought that's considered after.
	- annealer (compute) should do run many more iterations more than now by default (60k is way too low)
	- runs should also be increased from 24 (experiment in order to see a more ideal value)
	- ils should also be modestly increased from 6, as i believe 6 is too low and more perturbation rounds on the top-4 elite are enough important to deserve it.
	- seed should be auto-generated by default, only specified through cli flag.

  - `utils/` contains utilities/components/tools used by `core/` (the analyzer / annealer-compute).
    e.g. ansi.py, comfort.py, fingers.py, search, scorer...
    - ansi.py should live on its own sub-directory (it must be named one-word, and it should refer to the physical keyboard layouts or geometries of physical keyboards, like ansi/iso/matrix/etc.)

  - `config/` contains user-defined configurations, which the analyzer and layout generator logic should take into account.
    - inside should be a "config" file of some sort (maybe toml? but whichever format works best). inside this config file, the user should be able to define four things:
      1. general config parameters: corpora, physical layout (ansi/iso/etc), etc.
      2. fingermap: both analyzer and compute should use this by default. analyzer/generator's computed fingerings should never disobey fingermap unless specified through the alt list.
      3. alt list: the user defines their own alts based on specific bigram/trigram pairs (see example below).
      4. conditions: section for the user to allow/disallow specific properties (e.g. scissors[full/half, reverse]: true/false).
